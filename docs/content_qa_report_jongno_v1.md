# 종로 LLM 콘텐츠 QA 리포트 v1

> 작성: 이지선(ljs) · 이슈 #31 · 브랜치 `content-qa-design/ljs/v1`
> 베이스라인: `docs/jongno-baseline-v1.1.md` (4노드: 운현궁·익선동·인사동·광화문 + 사이드: 이순신)
> 방법론: `시나리오_구조화.md` 4-3절(Ashby et al. CHI 2023) — 4항목 Likert + 자동체크 3종
> 자동체크는 실제 병합 코드(`app/scenario/node_schema.py` `run_qa`/`infer_motivations`/`select_strategies`/
> `synthesize_npc`)를 이 저장소에서 직접 실행해 얻은 **실측 결과**입니다(재현 스크립트는 §5).

## ⚠️ 중요 제약 — 실제 LLM 생성물 평가 불가
현재 `.env` 설정상 `llm_provider = mock` (실 API 키 미설정) — `generate_mission()`을 실행해도 고정 더미
문구만 반환됩니다. 그래서 이 리포트는:
- **자동체크 3종·구조 필드 추론**: 실제 코드 실행 결과(진짜, mock 아님)
- **4항목 Likert**: "실제 LLM 생성물"이 아니라 **베이스라인 문서 자체의 품질**을 채점(정답지가
  비교 기준으로 쓸 만한지 자체 검증). 실제 LLM 생성물 평가는 **실 API 키 연결 후 재실행 필요**
  (W3 전 확인 권장 — pjh/kys 확인 요청 사항으로 별도 전달)

## 1. 자동체크 3종 결과 (실측, `run_qa()` 직접 실행)

베이스라인 문서의 `npc_dialogue`/`quiz`/`hint_ladder`를 각 노드 `overview`와 함께 `run_qa()`에 넣은 결과:

| 노드 | 정답유출 | 말투(~니라/허허) | 환각(overview 밖) | 비고 |
|---|---|---|---|---|
| 운현궁 | ✅ 없음 | ✅ 통과 | ✅ 없음 | 이상 없음 |
| 익선동 | ✅ 없음 | ✅ 통과 | 🔴 플래그 | "가마솥"(overview에 없는 서사 디테일), "운현궁"(이전 노드 단서 언급) 검출 — §3-1 |
| 인사동 | 🔴 플래그 | ✅ 통과 | 🔴 플래그 | 정답 "가"가 자연스러운 조사 "소리**가**"에 포함 — §3-2 (재현 확인, 문구 교정 후도 재현됨) |
| 광화문 | ✅ 없음 | 🔴 플래그 | ✅ 없음 | 세종대왕 대사가 "~니라/허허" 도깨비체가 아님(의도된 것) — §3-3 |
| 사이드(이순신) | ✅ 없음 | 🔴 플래그 | 🔴 플래그(약함) | 이순신도 역사인물이라 §3-3과 동일 사유. 환각 플래그는 "담아보게"류 활용형 어미가 근거 텍스트에 없어 잡힘(조사 스트리핑과 별개 문제, 어미 활용형까지는 `_stem`이 못 거름) |

**4/4 중 2개 노드에서 자동체크가 실제로 뭔가를 잡아냈고, 그 중 하나(§3-3)는 체크 자체의 전제(모든
NPC=도깨비체)가 이 시나리오의 의도(세종대왕=다른 말투)와 어긋나서 생긴 오탐입니다.** 아래 상세.

### 3-1. 익선동 환각 플래그 — 크로스노드 서사 언급
`run_qa`는 **해당 노드의 overview만** 근거로 삼습니다. 익선동 대사가 "운현궁에서 申時 단서를 얻어
왔구나"처럼 **이전 노드를 회상**하면, 이전 노드 이름이 이 노드 overview엔 없으니 무조건 미검증
어휘로 잡힙니다. "가마솥"은 진짜 서사적 디테일(overview에 없는 창작)이라 정당한 플래그입니다.
→ **연계 대사(7-C)는 이 체크가 구조적으로 오탐낼 수밖에 없음** — QA 시 사람이 "직전 노드 언급인지"
따로 걸러야 함. 자동화 개선(직전 노드 grants/overview도 근거에 포함) 제안.

### 3-2. 인사동 정답유출 — 1글자 정답의 조사 결합 오탐 (가장 중요한 발견)
`_quiz_answer_text`가 뽑은 정답 "가"는 이 시나리오의 자모 조합 퀴즈(S3_RIDDLE_UNLOCK) 특성상
1글자입니다. `단서_설계_규칙.md`의 S3 예시 자체가 `ㄱ, 益, 申時, 三`처럼 **전부 1~2글자**라
구조적으로 흔한 패턴인데, 문제는 `answer_leak`이 **순수 부분 문자열 매치**라는 것 — 조사 "가"
(주격조사, 예: "소리가", "무엇인가")가 자연스러운 한국어 문장 어디에나 등장합니다.
- H3를 "가장 크게" → "제일 큰"으로 바꿔도, H2의 "이을 소리**가**"에서 재현됨(조사라 회피 불가)
- `run_qa`의 환각 체크는 이미 조사 스트리핑(`_stem`)을 적용해 이 문제를 풀었는데, **정답유출
  체크(`answer_leak`, `_remove_answer_leak`)에는 같은 처리가 없음** — 동일한 어간 비교 로직을
  재사용하면 해결 가능해 보임
- **제안(pjh에게 전달 요청)**: `answer_leak`도 조사 스트리핑 후 비교하거나, 정답 길이 ≤2일 때는
  어절 경계 매치로 전환

### 3-3. 광화문 말투 플래그 — 세종대왕은 의도적으로 다른 말투
`_TONE_MARKERS = ("니라","허허","거라","구나","로다","느니")`는 "도깨비체" 전제입니다. 하지만
세종대왕은 `시나리오_MVP_예시.md` 원본부터 "위엄+자애" 말투(~는가/~네)로 의도적으로 다르게
설계됨 — 역사 인물 NPC(세종대왕·이순신 등)와 도깨비 NPC의 말투를 구분하는 게 서사 의도입니다.
- **제안(pjh에게 전달 요청)**: `run_qa`가 `npc.archetype`(현재 finale는 이미 `"guardian"`으로
  구분됨 — `synthesize_npc` 참고)을 보고 톤 마커 세트를 분기하거나, guardian/역사인물 archetype은
  이 체크를 스킵

## 2. 구조 필드 자동추론 vs 베이스라인 비교 (실측)

베이스라인이 수작업으로 정한 동기/전략/NPC를, 실제 TourAPI스러운 source(overview 등)를 넣고
`infer_motivations`/`select_strategies`/`synthesize_npc`로 **실제 코드가 자동 추론하면 뭐가
나오는지** 비교했습니다.

| 노드 | 동기(베이스라인) | 동기(자동추론) | 전략(베이스라인) | 전략(자동추론) | NPC(베이스라인) | NPC(자동추론) |
|---|---|---|---|---|---|---|
| 운현궁 | M1+M7 | **M1+M7 일치** | S4+S3 | S6(불일치, index순환) | 먹 도깨비 | 현판 도깨비(같은 heritage풀, 해시라 다름) |
| 익선동 | M6+M4 | M6만(불일치) | S7+S3 | S7만 | 한옥 도깨비 | 가마솥 도깨비 |
| 인사동 | M8+M7 | M6+M1(불일치) | S5+S3 | S6(불일치) | 붓장수 도깨비 | 됫박 도깨비 |
| 광화문 | M3 | M3+M1(거의 일치) | S6 | **S6 일치** | 세종대왕 | 수호 도깨비(하드코딩) |

### 발견 1 — 익선동 "S7+조각" 조합, 두 번 정정 (최종: 실제 문제 없음)
이 항목을 두 번 고쳤습니다 — 재검토 과정 그대로 남겨서, 최종 결론만 믿지 마시고 근거(아래 실행
결과)를 같이 봐주세요.

1. **최초 주장**: "spot 노드는 S7을 못 받고, kind=food/cafe 노드는 조각을 못 받아서 이 조합 자체가
   불가능하다" → **틀림**. `docs/jongno-baseline-v1.1.md`의 익선동 노드(`kind="spot"`, 전략에 S7
   포함, 조각 grants 포함)를 실제로 `validate_app_contract()`에 넣어 검증했더니 **통과**했습니다.
   `validate_app_contract`는 `kind="food"/"cafe"`일 때만 조각 grants를 막지, `kind="spot"`이면
   S7 전략과 조각 grants가 같이 있어도 계약 위반이 아닙니다.
2. **1차 정정**: "계약은 통과하지만 자동 추론 경로(`select_strategies`)에서는 S7이 spot 노드에
   절대 안 나온다" → **이것도 틀림**. 동기가 M6 하나뿐인 경우(예: `content_type_id=39`인 장소는
   `infer_motivations`가 무조건 `["M6"]`만 반환) `select_strategies(["M6"], mission_type,
   is_food=False)`를 실제로 호출해보면 **S7_PATRONIZE가 그대로 나옵니다** — M6에 대응하는 유효
   전략이 STRATEGY_TO_MOTIVATIONS 상 S7 하나뿐이라, 1차 후보 제외 후 최종 폴백(`reroll_strategy`)
   단계에서 결국 S7로 되돌아오기 때문입니다.

**최종 결론**: 익선동 설계(spot + S7 + 조각)는 계약도 통과하고, 동기가 M6 하나뿐인 흔한 케이스에선
자동 추론 경로로도 나올 수 있는 정상적인 조합입니다. **아키텍처 결정이 필요한 문제가 아니었습니다**
— kys/pjh에게 전달드렸던 이전 코멘트 초안(§4 "익선동 확인 요청")은 폐기해 주세요, 죄송합니다.

### 발견 2 — M8(물건 되찾기) 같은 서사 전용 동기는 overview에서 추론 불가
인사동의 "붓방망이를 잃어버렸다"는 완전히 창작된 NPC 사연이라 실제 장소 overview 어디에도 근거가
없습니다. `infer_motivations`는 overview 키워드(분실/잃어버 등) 기반이라 이런 순수 창작 동기(M8,
M9)는 애초에 자동 추론 대상이 아닙니다 — **이건 버그가 아니라 구조적 한계**: 이런 노드는 항상
수작업 정답지가 있거나, `enrich_quest(motivations=[...])`처럼 상위(generator)에서 수동 지정해야
함. 종로처럼 고정 큐레이션 데모 코스는 이미 이 경로(`motivations` 인자로 override)를 쓰고 있어서
실사용엔 문제 없음 — 다만 "일반 TourAPI 노드 자동생성"에서는 M8/M9류 동기가 잘 안 나온다는 걸
알고 있어야 함(기대치 조정용 기록).

### 발견 3 — 전략은 index 기반 순환이라 서사 다양성과 어긋날 수 있음
운현궁·인사동 둘 다 자동추론에서 S6_ACCUMULATE로 수렴했습니다(`stone_index=0`으로 계산해서—
실제로는 노드마다 index가 달라 결과가 달라짐, 이건 이 스크립트의 단순화 때문이지 실제 버그는
아님). 다만 "노드마다 다른 미션 타입" 다양성이 index 순환에 의존한다는 걸 보여줍니다 — 큐레이션
데모에서는 상관없지만(수작업 전략 고정), 일반 자동생성에서는 우연에 좌우됨.

### 발견 4 — finale NPC 이름이 "수호 도깨비"로 하드코딩됨
`synthesize_npc`가 `is_finale`이면 무조건 `"수호 도깨비"`를 반환합니다. 베이스라인은 광화문에
실존 역사 인물 "세종대왕"을 쓰는데, 지금 코드로는 이 이름이 절대 안 나옵니다. 종로 데모처럼
"피날레 NPC를 역사 인물로 고정"하려면 `enrich_quest`에 NPC override 경로가 필요 — **pjh 확인
요청 사항**.

### 발견 5-보충 — `build_success()` 실행 결과와 베이스라인 문서 대조(실측)
`actions` 배열을 실제 `build_success()`에 넣어 `success` 필드가 문서와 일치하는지 5개 노드 전부
대조했습니다. 익선동에서 불일치를 발견해 문서를 고쳤습니다: 식음 동반 노드라도 `kind="spot"`이면
`purchase(optional)` 뒤에 붙는 성공 조건은 `"one_of:purchase_verified|tap_done"`이지,
`kind="food"/"cafe"` 전용 문구인 `"one_of:purchase_verified|free_alternative_done"`이 아닙니다
(두 문구는 서로 다른 코드 분기 — 전자는 일반 액션 순회, 후자는 `is_food` 전용 하드코딩 반환).
나머지 4개 노드(운현궁·인사동·광화문·사이드)는 실행 결과가 문서와 정확히 일치했습니다.

### 발견 5 — `actions[].choices[].text`가 항상 동일한 3개 범용 문구
`compile_actions`→`build_choices`는 노드와 무관하게 "무슨 일이 있었는지 자세히 묻는다." 등 고정
3문장을 반환합니다(코드 주석에 "문구는 LLM 슬롯 대상(#31)"이라 명시돼 있음). 베이스라인 문서의
노드별 선택지 텍스트(§1~4의 "선택지" 표)는 현재 실제로 이 필드에 채워지는 경로가 없습니다.
→ **#31 잔여 스코프**로 확인: 이 필드까지 이번에 채울지, 이후로 미룰지 kys/pjh와 조율 필요.

## 3. Ashby 4항목 정성 평가 — 베이스라인 문서 자체 평가

(실 LLM 생성물이 아니라 **베이스라인이 비교 기준으로 쓰기에 충분한 품질인지** 자체 점검. 1~5 Likert)

| 노드 | 유창성 | 일관성(장소·페르소나) | 참신성 | 창의성 | 코멘트 |
|---|---|---|---|---|---|
| 운현궁 | 5 | 5 | 4 | 4 | 사진→발자국 추적 패턴(P4)이 다른 노드와 확실히 다름 |
| 익선동 | 5 | 4 | 3 | 3 | 어휘 퀴즈(益)는 무난함(발견1 재검토 결과 구조 문제 없음으로 정정됨) |
| 인사동 | 5 | 5 | 4 | 4 | 자모 조합("ㄱ"+"ㅏ"="가")이 훈민정음 테마와 잘 맞물림 |
| 광화문 | 5 | 5(역사인물 톤 분리 의도적) | 4 | 3 | 엔딩 분기가 단순(2택)이라 창의성은 중간 |

전체 평균: 유창성 5.0 / 일관성 4.75 / 참신성 3.75 / 창의성 3.5 — 베이스라인 자체는 비교 기준으로
쓰기에 충분한 완성도. 참신성·창의성이 상대적으로 낮은 건 4노드 모두 "사진/AR탐색+퀴즈" 뼈대를
공유하기 때문(§1 원본 문서도 인지하고 있는 특징, 패턴 카탈로그 P1~P6 조합으로 완화하는 설계).
